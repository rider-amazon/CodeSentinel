# 约束规则

> 执行阶段的硬性约束。违反任一条即视为执行越界。

---

## R1. 不得改无关模块

每次改动**仅限计划中列出的文件**，且须在 `rules/scope.json` 的 `allow` 范围内；`deny` 列表中的文件（如 `.env`、`data/`、`report/`、`experiment/config.json`）一律禁止改动。

若发现需要额外改动，必须：
1. 先回到计划阶段，把新文件加入改动范围表；
2. 说明原因；
3. 再继续执行。

**自动核对**：执行完后运行 `python harness/scripts/harness.py --root . check-scope`，脚本会扫描 git 实际改动并与 `allow`/`deny` 比对——超出 allow 或命中 deny 会标红并返回非 0，此时须回到计划补充说明或不提交该文件。

**禁止行为**：
- ❌ "顺手"重构未在计划中的文件
- ❌ 为了方便而改公共工具函数（除非计划明确包含）
- ❌ 删除/移动未被列出的文件
- ❌ 改动 `deny` 列表中的密钥/数据/产物文件

## R2. 不得擅自引入未比选的新依赖

新增第三方包必须满足以下条件之一：
1. 已在 `requirements.txt` 中存在（只是之前没用到的已有依赖）；
2. 经过比选（至少对比 2 个候选方案），并在计划文档中说明选择理由。

**禁止行为**：
- ❌ 直接 `pip install xxx` 并写进代码而不更新 `requirements.txt`
- ❌ 引入重量级框架（Django/React/Vue 等）——本项目技术栈已定为 FastAPI + 原生 JS

## R3. 先读后改

对任何已有文件做编辑前，必须先用 `read_file` 工具读取当前内容。
不得凭记忆或旧版本猜测内容来构造编辑锚点。

## R4. 密钥不入库

绝不把 API Key / 密码 / Token 写进源码或提交的配置文件。
密钥只能通过环境变量（`os.environ`）或 `.env`（已在 `.gitignore` 忽略）读取。

## R5. 假实现必须标注

若用临时假实现支撑功能（降级占位、固定返回值等），必须同时满足：
1. 代码中有注释标明 `# TODO: 假实现，待 xxx 替换`；
2. 在演示说明 / 差距清单 / 当日报告中标明"假实现"及原因；
3. 不得对外宣称该功能"已完成"。

## R6. 编码规范

- 新增 Python 文件必须通过 `python -m py_compile <file>` 语法检查；
- 不破坏现有功能（改完后主路径仍能跑通）；
- 中文注释统一用 UTF-8，不在源码文件中写 BOM。

---

## 违规处理

若执行中发现违反上述规则：
1. 立即停止当前改动；
2. 回滚违规修改；
3. 回到计划阶段，补充说明后再执行。
